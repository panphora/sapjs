When to use it

Use sapjs when your whole app lives in one HTML file, different parts of the page need to react to each other and you want all the state stored in the document itself.

  • State stays in the document. Records are HTML elements and fields live on their attributes and controls, so the file holds the data with no separate JavaScript store to drift from the page.
  • Formulas live in attributes. You declare fields and derived values with bind, items, calc: and text instead of writing render code, and any edit updates the rest of the page.
  • Views and editors are built in. Attributes like trigger-add, each=, detail= and transient handle adding rows from a form, sorted and filtered views, detail panels and search text that never saves.
  • Every change re-reads the DOM. Each pass rebuilds state from the live markup so devtools edits and live sync work the same as a click, and a change at 10,000 records still takes under 40 ms in Chrome.

How it works

Say you keep a reading log as one HTML file. Each book is a <tr> in a table. The day you started and the day you finished are attributes on that row. An <output> under the table shows how many books you finished. Open the file in a text editor and every book is there as markup.

The count is a formula in an attribute on that <output>. Add a book or change a date, and sapjs re-reads the page and updates the count. Change a date by hand in devtools and the count updates, the same as after a click. Each change reads the books fresh from the rows, so there is no JavaScript copy to drift from the page. How it works shows each step of that re-read.

The last count is written inside the <output> in the file, so it shows before any script runs.

I think sapjs works best when the interface and the data both fit in that one file. You edit the file and share it like any document. Add a finished date to a row in a text editor, open the file, and the count goes up by one. Send the file to a friend and they get the app with every book in it.

ClayJS is the library that saves an HTML file back to its host and syncs it between tabs. Saving takes ClayJS, or another client like it, on a host that accepts saves. Put persist on each input, textarea and select in a record, so what you type reaches the saved markup.

What you can build

The apps that fit are lists of records. An expense tracker is rows of expenses and a total. A board is columns of cards. With sapjs, each record is an element in the file, and each number is a formula in an attribute.

Expense tracker

A form adds an expense as a new row. A calc: attribute sums the amounts, and text:usd2 paints the total as $54.50.

trigger-add · calc: · text:usd2

Kanban board

Columns hold cards as nested lists. Drag a card to another column with ClayJS sortable, and the move saves as the new order of the markup. Click a card and a <dialog> opens to edit it.

items= · detail=

Notes

The notes are saved records. The list you see is an each= view, sorted by title and filtered by a search box. The search box carries transient, an attribute that keeps the search text out of the saved file. A detail= panel edits the open note.

each= · transient · detail=

Reading log

Each book stores the day you started and the day you finished. days() shows how long each one took, and count() shows how many you finished.

calc: · days() · count()

Contacts

Click a name and a detail= form edits that contact. A sort: button sorts the list by any field, and confirm= asks before a delete.

detail= · sort: · confirm=

Invoice

Each line computes its own total. The invoice sums the lines and paints $1,234.50. move:up and move:down reorder the lines.

calc: · sum() · move:

If you want running code to read, the guide walks through an expense tracker, a Kanban board and a notes app, and each one runs in the sapjs test suite.

Where this library struggles

Tens of thousands of records

At 10,000 records a change still takes under 40 ms in Chrome. The cost is the file itself: every row is saved markup, so saving takes about 400 ms and a list of 10,000 text boxes takes over a second to lay out. Past that, measure before you build on it.

Data some viewers must not see

The data is in the markup. Anyone with the file has all of it.

Mostly a window onto a server

If the records live behind an API, keeping them in the DOM gives you nothing back.

An editor built on a rich-text library

sapjs state is plain text. A rich-text editor goes inside an element with sap-ignore, an attribute that marks a region sapjs does not read. An app built around such an editor ends up mostly editor code.

A page with a strict Content Security Policy must allow 'unsafe-eval', because sapjs compiles its formulas at runtime with new Function.

Quick start

On its own, the app runs and recomputes. Nothing saves.

<script src="https://cdn.jsdelivr.net/npm/@panphora/sapjs/dist/sap.min.js"></script>

With ClayJS, the file saves itself on a host that accepts saves. Load sap.js after clay.js, and see the guide for the rest.

<html autosave>
<script src="https://clayjs.com/v1/clay.js?plugins=sync,sortable,undo"></script>
<script src="https://clayjs.com/v1/sap.js"></script>
