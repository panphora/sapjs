sapjs · reactive HTML in one file

A script tag that makes one HTML file a working app

You have a checklist in an HTML file, and you want it to count what is left. sapjs is a script tag that does that with attributes. Each task is an element, and the count is a formula in a text= attribute. Every change makes sapjs re-read the page and update the count.

1 task left

Check a box and the count drops. Inspect that checkbox and it now carries a checked attribute, because persist writes the value into the markup. Add a task and a new <li> joins the list. This page runs no JavaScript of its own, only sap.min.js.

<main sap id="hero-demo">
  <form trigger-add="todos">
    <input bind="title" placeholder="Add a task" required>
  </form>
  <ul items="todos">
    <li item template>
      <input type="checkbox" bind="done" persist>
      <span bind="title" contenteditable="plaintext-only"></span>
      <button trigger-remove>x</button>
    </li>
    <li item>
      <input type="checkbox" bind="done" persist checked>
      <span bind="title" contenteditable="plaintext-only">Buy milk</span>
      <button trigger-remove>x</button>
    </li>
    <li item>
      <input type="checkbox" bind="done" persist>
      <span bind="title" contenteditable="plaintext-only">Call the landlord</span>
      <button trigger-remove>x</button>
    </li>
  </ul>
  <output text="plural(count(state.todos, t => !t.done), 'task', 'tasks') + ' left'">1 task left</output>
</main>

That is the whole app. The tasks are <li> elements. The count is the formula in one text= attribute, and the text inside <output> is its result.

sapjs runs in any current browser from one script tag. Saving needs ClayJS on a host that accepts saves: HTML Clay, Hyperclay Local or hyperclay.com.

01

When you would use it

You want a small tool that is one file you own.

I think sapjs works best when the interface and the data can both live in one file. You can open it in a text editor, change a line, and it still works.

the file is the app

Records are markup

Each record is an element, and each field is an attribute or its text. Put persist on each control you type into or check. On a host that accepts saves, saving the page then saves every record. A saved file already holds its computed numbers in the markup, so it shows them before any script runs.

any change is input

Every change takes the same path

Live sync is ClayJS keeping open tabs and devices in step. A keystroke, an edit to the markup in devtools and a live-sync merge from another tab are all changes to the page. sapjs re-reads the page after each of these changes. One exception: after an undo or redo, a control you typed into or checked keeps your value, and sapjs counts that value, until the short re-sync script in section 8 of the guide runs.

no build

One script tag

About 59 KB minified and about 20 KB gzipped. No bundler, no JSX, no compile step. The file opens straight from disk.

loud errors

Errors name the element

Every error sapjs logs has a code and the element's CSS path. Write to a name of four or more letters that is a letter or two off a declared field and it prints E12 with did you mean; any other new name becomes a new field. A misspelled read in a plain text= paints a blank and logs nothing.

views stay out

Searching changes no saved bytes

A transient field is one that is never saved. An each= attribute draws a view of a list. A transient field can hold the search text, and an each= view can draw the matching records. A ClayJS save leaves both out, so searching leaves the saved file as it was.

ClayJS or alone

Saves and syncs with ClayJS

On a ClayJS host, the file saves itself in edit mode, and the sync plugin syncs it between tabs. When ClayJS syncs, sorts or undoes, sapjs recomputes. Without ClayJS it runs the same and saves nothing.

02

What you can build

Small tools you would keep in one file.

The small line above each name lists the sapjs features that do the work.

trigger-add · calc: · text:usd2

Expense tracker

A form adds an expense as a new row. A calc: attribute sums the amounts, and text:usd2 paints the total as $54.50.

nested items= · detail=

Kanban board

Columns hold cards as nested lists. Drag a card to another column with ClayJS sortable and each column's count updates. Click a card and a <dialog> opens to edit it.

each= · transient · detail=

Notes

The notes are saved records. The list you see is an each= view, sorted by title and filtered by a search box. A detail= panel edits the open note.

calc: · days() · count()

Reading log

Each book stores the day you started and the day you finished. days() shows how long each one took, and count() shows how many you finished.

detail= · sort: · confirm=

Contacts

Click a name and a detail= form edits that contact. A sort: button sorts the list by any field, and confirm= asks before a delete.

row calc: · sum() · move:

Invoice

Each line computes its own total. The invoice sums the lines and paints $1,234.50. move:up and move:down reorder the lines.

If you want running code to read, the guide walks through an expense tracker, a Kanban board and a notes app, and each one runs in the sapjs test suite.

03

How it works

One change, one pass.

Check a box in the demo and sapjs runs one pass over the app.

1IntakeRead every field (state=, bind, items=) into fresh objects. A state= attribute declares a field on an element.
2ComputeRun the calc: fields in dependency order.
3PaintUpdate text, show, attr: and class:. Write only what changed.
4DiscardThrow the objects away; the next pass rebuilds them, reading every saved field from the page.

Each pass rebuilds the app's data from the page, so no copy of the saved data in JavaScript can drift from it.

A paint writes only when the new value differs from the old one. The demo's file already said 1 task left, so loading it changed nothing. The console reports it as mount writes 0.

React keeps its state in JavaScript and draws the DOM from it. In a file that saves itself, the DOM is what gets saved, and live sync rewrites it from outside. sapjs reads its state from there every time.

04

Where it stops

If your app looks like one of these, pick something else.

size

Thousands of records

Each change re-reads the whole app, and every row is saved markup. I have tested apps with 500 records, and sapjs has a 1,000-record benchmark. Past that, measure before you build on it.

privacy

Data some viewers must not see

The data is in the markup. Anyone with the file has all of it.

shape

Mostly a window onto a server

If the records live behind an API, keeping them in the DOM gives you nothing back.

rich text

An editor built on a rich-text library

sapjs state is plain text. A rich-text editor goes inside a sap-ignore region, which sapjs does not read. An app built around such an editor ends up mostly editor code.

Expressions compile with new Function, so a Content Security Policy has to allow 'unsafe-eval'.

Start

One script tag.

On its own, the app runs and recomputes. Nothing saves.

<script src="https://cdn.jsdelivr.net/npm/@panphora/sapjs/dist/sap.min.js"></script>

With ClayJS, the file saves itself in edit mode on a host that accepts saves: HTML Clay, Hyperclay Local or hyperclay.com. A file opened from disk does not save. The sync plugin syncs it between tabs. Load sap.js after clay.js. If your app has inputs, also add the re-sync script from section 8 of the guide.

<script src="https://clayjs.com/v1/clay.js?plugins=sync,sortable,undo"></script>
